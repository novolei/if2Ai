## Smoke-discovered gaps (in chronological order — these are the bugs the design didn't anticipate)

### A.2-wiring: 3 failures all surfaced in one session

1. **`tokio::spawn` panics in Tauri `setup` hook** (no Tokio reactor entered there). Fix: `tauri::async_runtime::spawn`.
2. **Manual `daydream_run_cycle` command returned report via Tauri invoke result but didn't emit the `runtime_event` envelope.** Frontend projection only saw idle-fired cycles. Fix: emit envelope inside the command after running the cycle.
3. **Settings window is a separate Tauri webview.** `RuntimeProjectionWiring` was only mounted in `App.tsx`, not `SettingsApp.tsx`. Settings window never subscribed to `runtime_event`. Fix: mount `wireRuntimeProjectionListeners()` in `SettingsApp` too.

**Pattern:** all three were "wiring assumed to exist that didn't" — the kind of thing that compiles fine but only fails at runtime when surface meets surface.

### A.4 → A.3.2-fix discoveries: `promoted: 0` chain

1. **`args_summary` was empty** (A.3.2 placeholder). Hypothesis: SelfReflector needed concrete tool intent context. Re-smoke after fix: still `promoted: 0`. Confirmed: data wasn't the bottleneck.
2. **Reflector Rule 2 (clean execution, 0.8 confidence) was structurally unreachable**: gated on `trajectory.turns.len() > 1`, but Wave A.3 producer creates **exactly one TurnRecord per run** (Q1=B brainstorm). Rule 1 (frequent tool combo, 0.65) was the only candidate, always rejected by 0.7 floor. **Real fix**: replaced gate with `(turns.len() > 1 || successful_tool_calls >= 2)`. After this: first `promoted: 1` ever observed.

**Pattern:** producer shape and consumer expectations had drifted apart silently. The brainstorm decision (Q1=B per-run trajectory) was correct for our IPC model; the reflector was designed for a different (multi-turn task) shape and the mismatch was invisible until smoke demanded `mutated > 0`.

### `todo_ledger_incomplete` false positive (discovered during same smoke)

User issued `'在工作目录创建一个新的文件夹叫eee'`:
- mkdir tool ran successfully ✓
- but UI surfaced `Agent 执行异常 / todo_ledger_incomplete` ✗

Root cause chain (5 steps):
1. `is_tool_required_work_intent` matched `创建` + `文件夹`
2. Flipped into AutonomousWork → triggered TodoWrite discipline
3. Agent opened 1-step TodoWrite ledger, ran mkdir, model_stop'd without formally closing
4. Safety check `terminal_status_with_todo_ledger` saw unfinished work → flipped status
5. UI surfaced synthetic terminal status as hard agent failure

**Fix**: thread `has_successful_mutating_tool` into safety check. Bypass when **single-step plan AND mutating evidence present**. Multi-step abandonments still flag correctly.

**Pattern:** safety checks designed for genuine multi-step abandonment cases over-fired on simple one-shot tasks the classifier promotes to autonomous_work.

## Locked design decisions (with rationale, in case future-you wants to revisit)

| Decision | Choice | Why | Where to revisit |
|----------|--------|-----|------------------|
| Daydream default state | `enabled: false` (opt-in) | Background LLM cost should be deliberate | If telemetry shows users want it on by default after enabling once |
| Trigger model | Manual + idle@30min (drop session-end) | Session-end duplicates idle for normal "user closes app" path; risks blocking shutdown | If users want explicit "run after each turn" mode |
| Strategy as budget knob | Conservative / Balanced / Aggressive enum (no separate `llm_budget_tokens`) | Strategy already encodes intent; separate budget knob creates incoherence | If LLM-augmented insights (A.5) need finer-grained per-call budget |
| Default strategy | Balanced (Prune + Merge + Reflect) | Opted-in user expects more than just decay sweep; Aggressive's Refresh step has lowest legibility per token | Telemetry on cost vs. value of Refresh step |
| Failure visibility | Status row only (no toast) | Toasts interruptive for non-critical bg work; status row builds trust by showing successes too | If a user reports they want push notifications |
| Persistence | In-memory ring of 100 trajectories (no JSONL) | Insights persist to procedural SQLite anyway; bounded blast radius for opt-in feature | If telemetry shows trajectory loss matters (probably never) |
| Trajectory granularity (Q1) | B = per-run trajectory keyed by session_id | Matches existing run lifecycle; finalized when `run_turn` returns | If reflector grows multi-turn-aware rules that benefit from cross-run context |
| TrajectorySource impl | Stub (`EmptyTrajectorySource`) initially → `CollectorTrajectorySource` (in-memory ring) | Q1 lossy adapter from `learning::trajectory` (ShareGPT) → `evolution::trajectory` (task-execution) was rejected because it'd produce garbage insights polluting procedural memory | If `learning::trajectory` ever grows the per-turn fields (`success`, `tool_calls`, `outcome`) |
| TurnRecord richness (Q3) | B = full (with `tool_calls`, `agent_action`); `args_summary` populated streaming-only; `self_assessment: None` | LLM self_assessment too expensive per turn; non-streaming `summary.tool_results` lacks input args (would need runtime layer threading) | A.5 LLM extraction; `args_summary` non-streaming if telemetry shows IPC users matter |
| Outcome detection (Q4) | A = at run end (Success { quality: 1.0 } on Ok arm; Failure { category, root_cause } on Err arm) | Simple, no LLM cost; supervisor lifecycle already produces the signal | LLM-classified outcome quality if reflection rules need finer signal |
| Instrument location (Q5) | A = turn_service (run.rs + stream_task.rs) | Where success/failure outcome is determined; commands/agent layer too thin | If Teams introduces parent_run_id and we need cross-run correlation |
| Procedural display (Q1 of A.4) | B = section in DaydreamSettingsSection | Causal narrative "you enabled daydream → here's what it learned"; avoids 9th tab | If a power-user mode wants raw entry browsing |
| Insight metadata (Q2 of A.4) | B = category + trust + content (no full provenance tree) | Category derives from key; trust bumped per re-encounter (proxy for confidence); no schema change | If insight provenance tree becomes a debugging need |
| Cycle visibility (Q3 of A.4) | C = reflect breakdown in history modal | Drops trajectory-list viewer (ephemeral until JSONL); shows the SelfReflector funnel directly | If trajectory persistence lands |

## Architecture & contract notes (gotchas worth remembering)

- **Settings is a separate Tauri webview.** Anything that subscribes to `runtime_event` must be mounted independently in `SettingsApp` — `RuntimeProjectionWiring` in `App.tsx` doesn't propagate. Same for any future window (chat-only mini-window, popout, etc.).
- **`tauri::async_runtime::spawn` not `tokio::spawn`** in `setup` hooks. Setup runs synchronously on the main thread before `.run()`; no Tokio reactor is entered. Pattern: `desktop_host/setup.rs`, `commands/settings.rs`, `commands/memory/daydream.rs` already use this.
- **Two `Trajectory` types are structurally incompatible.** `learning::trajectory::Trajectory` is ShareGPT-shaped (id, conversations, model_id, temperature). `evolution::trajectory::Trajectory` is task-execution-shaped (turns: Vec<TurnRecord>, outcome). Don't try to translate one to the other.
- **Reflector rules are confidence-floored.** `MIN_INSIGHT_CONFIDENCE: 0.7`. To extract a new insight type, the rule must emit ≥0.7 OR the floor needs to be lowered (would spam procedural memory with `Clean execution of 'what's 2+2'` noise — current floor is correct).
- **Procedural entries' `trust_score` is a confidence proxy.** Bumped by `TRUST_INCREMENT: 0.1` on every re-encounter. Useful for UI rendering ("trust high/med/low") without storing a separate field.
- **Manual + idle daydream emit the same envelope shape.** Frontend should treat `payloadFamily: "completed" | "failed"` uniformly; no need to distinguish trigger source on the consumer side.
- **`StepOutcome.extracted_count` / `rejected_count` are reflect-step-only.** Other steps emit `None`. UI must handle `undefined` gracefully (legacy cycles also have `undefined`).
- **`is_tool_required_work_intent` over-classifies simple one-shot tasks.** "创建文件夹eee" matches `创建` + `文件夹`. todo_ledger safety check now bypasses single-step plans with mutating evidence, but the classifier itself is still aggressive.

## Deferred work — items by priority

### Likely worth (collect data first)

- **A.5 LLM-augmented insight extraction** — current rule-based reflector produced 4 candidates (3 rejected, 1 promoted) on user's smoke. If real-world usage shows similar low-yield, LLM augmentation could help. But: cost. Decision needs telemetry first.
- **`args_summary` enrichment in non-streaming `run.rs`** — would require runtime layer threading to expose input alongside result. Most chat traffic is streaming, so low-priority unless IPC users appear.
- **`is_tool_required_work_intent` classifier tuning** — currently catches simple one-shot tasks. Bypass in todo_ledger safety check works around symptom; real fix is making the classifier smarter (e.g. "1-line message about an artifact = NOT autonomous_work").

### Probably never

- **JSONL trajectory persistence** — in-memory ring + insights persisted to SQLite means restart loses unconsumed trajectories only. Bounded blast radius for opt-in feature.
- **Full insight → cycle → trajectory provenance tree** — would need new join column linking procedural entries to source `cycle_id`. UI value unclear.
- **Standalone Trajectory History viewer** — ephemeral until JSONL persists; not worth building.
- **Reflector `reflect_on_failure` Rule 1 tuning** — current 0.9 confidence on `error_rate > 0.5` should already work for single-failed-turn runs (1.0 > 0.5). Wait until real failure run shows up before tuning.

### Tech debt

- **Pre-existing baseline drift** — fully cleaned in PR #9 + #10. Both `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` are green on `vnext-base-2026-05-08`. CI can be tightened to enforce.
- **`is_tool_required_work_intent` aggressive matching** — see above. Behavior workaround in place; underlying logic could be refined.

## Lessons from this session

1. **Smoke is the only real verification.** Cargo check + cargo test passed for every PR but found 6 distinct user-visible bugs only when the app actually ran (3 in PR #3 smoke, 2 in PR #8 smoke, 1 in user's chat after PR #7 smoke).

2. **Make the data path observable before tuning.** Each "promoted: 0" mystery was diagnosed in minutes once we added the `extracted/rejected/promoted` breakdown to the reflect step. The breakdown is what told us "the data path is fine, the rule is wrong" instead of "is the data path even working?"

3. **Producer shape and consumer assumptions drift silently.** Q1=B (per-run trajectory) was the right call for our IPC model; the reflector was designed for multi-turn tasks. Two correct designs, incompatible together. Caught by smoke, not by code review or types.

4. **Safety checks need an "evidence override" path.** `terminal_status_with_todo_ledger` correctly fired on unfinished TodoWrite ledgers, but didn't account for "mutating tool succeeded → user got the work even if ledger isn't formally closed." Generalize: any safety check that gates on process compliance should consider outcome evidence as a release valve.

5. **Re-exports break differently in `--lib` vs `--all-targets`.** `pub use` lines that the bin half consumes via `generate_handler!` macro show as unused under `--all-targets`. The macro is invisible to clippy. `#[allow(unused_imports)]` per-line with a brief "consumed by macro" comment is the right disposition.

6. **Bundling related fixes in one PR is OK if rationale is documented.** PR #8 shipped 3 related commits (`args_summary` data, reflector rule alignment, todo_ledger bypass) all surfaced by one smoke session. Reviewer-friendly when the body explains "all corrections to the same surface, diagnosed in one sitting." Independent revertability per commit kept the bundle honest.

7. **Pre-existing baseline drift is debt.** Every PR review burned cycles asking reviewers to ignore unrelated fmt/clippy noise. PR #9 + #10 absorbed this in 2 small PRs. Should have done this earlier.

8. **`tauri::async_runtime` is the codebase pattern**, not raw `tokio::spawn`. Setup hooks, command handlers, and any background task spawned outside an async context should use it. The codebase already had 5+ examples of this; my plan didn't notice them.
